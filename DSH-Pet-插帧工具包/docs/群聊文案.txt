━━━━━━━━ 第 1 条：这是个啥 ━━━━━━━━

发个自己在做的小工具，桌宠素材插帧用的。

【一句话】
把 webm 从 24fps 插到 48 / 72 / 90 / 120fps，保留透明通道，
输出还是能直接塞回桌宠的 webm。只做插帧，不做超分。

【重点：格式全自动，你什么都不用挑】
下面这些类型都逐项实测过：

  · VP9 + 透明通道（桌宠素材 / 动态壁纸）→ 透明通道原样保留
  · 不透明 VP9（普通视频 / 录屏）→ 输出也不会多塞没用的 alpha
  · VP8（老编码的 webm）→ 自动识别，输出转成 VP9
  · 各种分辨率（320×240 / 360×200 / 640×360 / 1280×720）
    → 尺寸不用凑整，RIFE 自己会处理
  · 带音轨的 webm → 音轨原样搬过去，不重新编码

说人话就是：带透明的它不会给你弄丢，带声音的它不会给你弄没。
市面上一堆插帧工具是出 mp4 的，而 mp4 的 H.264 根本没有透明通道
—— 素材一过就平了。这个工具只出 webm，就是为了保住透明。

【输入格式全自动认，输出统一是 webm】
格式识别整个做成了自适应，因为有人提醒「作者以后可能要换码」。

  认的输入：webm / mkv / mp4 / mov / m4v / avi / wmv / flv / ts /
            mpg / mpeg / ogv / 3gp / webp / gif / apng
  编码也自动认：VP9 / VP8 / AV1 / H.264 / MPEG-4 …… 都行
  音轨自动处理：opus / vorbis 原样复制；aac / mp3 自动转 opus
  输出：永远是 .webm

为什么输出写死成 webm：带透明通道的视频，实际能用的容器只有它。
而且 ffmpeg 是按后缀选封装格式的，不写死的话 mp4 喂进去会原样吐一个
mp4 出来（里面塞着 VP9、透明还丢了），等于废文件。

说人话：带透明的它不会给你弄丢，带声音的它不会给你弄没。
市面上一堆插帧工具是出 mp4 的，而 mp4 的 H.264 根本没有透明通道
—— 素材一过就平了。这个工具只出 webm，就是为了保住透明。

还有个细节挺有意思，顺便说一下：
GIF 这类格式经常"声明"自己有透明通道、实际上根本不用。拿群里
抓来的一张真实表情包实测 —— 它解出来是带 alpha 的，可整段 100% 的
像素都是不透明的。原来的版本会照着声明白跑一整轮插帧，白等 30% 时间。

现在改成：拆完帧先把 alpha 扫一遍，整段真没有透明像素就不跑那轮。
（判不准的时候一律当"有 alpha"，宁可不省也绝不把真透明丢掉。）

顺便把一个物理事实说清楚（这条挺重要）：
mp4 容器本身装不下透明通道。 带 alpha 的素材一 remux 进 mp4，
透明当场就没了（yuva420p 变 yuv420p）。这是格式的限制，不是工具的毛病，
谁来做都一样。要透明，素材只能用 webm 或 mkv 存。

【怎么用，两种随便挑】
· 小白版：双击「启动界面」→ 选文件夹 → 填帧率 → 点「开始插帧」。
  有实时日志，跑的时候界面不会卡死。
· 极客版：命令行走，支持指定单个文件、自定义输出目录。

图形界面用的是 Python 自带的 tkinter，一个第三方库都没引，
所以整个包才几十 KB（不会像 PyQt 那样多出几百兆）。

· 目标帧率在 config.json 里改，填多少都行，脚本自己读源帧率算倍数。


━━━━━━━━ 第 2 条：实测数据（这段最值得一看）━━━━━━━━

【先说一件比较硬的事：同一台机器双系统各跑了一遍】

测试机是双系统，Windows 和 Linux 装在同一台机箱上：
  i7-6700 / 16G / RTX 2060 6G / 机械盘 + SSD

所以下面的数据不是"朋友说能跑"，是同一套硬件、同一套素材、
两个系统各跑一遍。硬件一致，可比。

【Windows 实测（Windows 10 专业版 22H2）】
素材：640×360 / 24fps / 4.9 秒 / 带透明通道 / 118 帧
目标：插到 48fps（2 倍），输出 236 帧

  拆彩色帧 ......... 0.3 秒
  拆透明通道 ....... 0.3 秒
  RIFE 彩色插帧 .... 6.1 秒
  RIFE 透明插帧 .... 2.8 秒
  合成编码 ......... 5.8 秒
  ────────────────────────
  合计 ............. 15.3 秒

输出规格校验通过：640×360 / 48fps / 带透明通道 / 时长一致。

【和 Linux 对比】
同样规格，Linux 这边折算下来大约 2.35 秒耗时 / 秒素材，
Windows 是 3.11 秒 / 秒素材 —— Windows 慢约三成（NTFS + 不同 ffmpeg
构建，正常范围），但两边都是"十几秒出一段"的量级。

【顺便回答一个肯定会有人问的：这玩意到底用不用显卡？】
用。RIFE 那两步占了总耗时的 58%，拆帧和编码（也就是磁盘 IO）占 42%。
它是 rife-ncnn-vulkan，走 Vulkan 跑显卡的。
那两步要是掉到 CPU 软件渲染，一段素材就是几十分钟起步，不是十几秒。

【性能这块也下过功夫（最新一版提速了 25%）】

把整条流水线逐段计时之后发现一件反直觉的事：最贵的不是插帧，是编码，
占了总耗时的一半以上。而 ffmpeg 里 VP9 编码的默认值是「最慢最好」，
本工具一个旋钮都没设。

调完之后：

  整条流水线    25.1 秒 → 18.8 秒
  总 CPU 工作量 少了 40%
  平均占用      2.1 个核

还做了自动调度 —— 脚本会自己探你的电脑有几个核，然后：
  · 核多的话根本不去限制线程（限了只是白白变慢）
  · 但会把优先级压低：你机器闲的时候它全速跑，
    你一开别的程序它自动让路
  · 实测：机器空着时降优先级是零成本；机器被压满时，
    对用户的干扰从 +11.5% 降到 +5.2%

config 里有个「性能模式」，默认 auto，一般不用动。
嫌它占 CPU / 风扇吵，可以改成「省电」—— 平均占用能压到 1.5 个核，
代价是慢 40% 左右。

顺便说：核显能跑。拿这台的 Intel HD 530 实测过，
比独显慢 3.3~3.5 倍，一段素材从 19 秒变成 43 秒 —— 能用，不算快。
但画质一模一样（逐像素平均差 0.0132/255，有些帧逐字节相同）。

【画质，确实认真比过】
把全部 106 个片段扫了一遍，挑出动作最猛的那个（帧间差 22.0，
比一般片段高 1.4 倍），在峰值动作区间按「插帧相位」对齐取帧、
放大 3 倍逐像素比对 ——
插帧后的边缘发虚度全部落在两个源帧之间，
没看到黑洞、融化或双层幻影，120fps 也没看出来。

【低帧素材也试了】
8fps 的素材硬插到 48fps（6 倍）、12fps 插到 48fps（4 倍），都没崩。
量化下来：相邻帧最大跳变从 33.8 降到 8.5，
"跨源帧处 / 纯补帧处"的比值是 0.79 ~ 0.83（越接近 1 越平滑）。
对照组是用 ffmpeg 直接帧复制升帧，那个比值是 0，抖动肉眼可见。


━━━━━━━━ 第 3 条：怎么拿、要装啥 ━━━━━━━━

【包按系统分了，你只需要下对应自己系统的那一个】

  Windows 用户 →「1-开箱即用版-Windows.zip」（85 MB，推荐）
                 程序全在里面：ffmpeg、ffprobe、rife 本体、模型、
                 运行库，一个不缺。解压出来双击就能跑，不用下、
                 不用装、不用配。唯一的门槛是电脑上要有 Python 3.8+，
                 装的时候记得勾上「Add Python to PATH」，不勾后面全废。
                 （要是你早就自己装好 ffmpeg 和 rife 了，也可以下
                   「2-精简版-Windows」，体积小得多。）

  Linux 用户   →「3-精简版-Linux-v0.8.zip」（不到 1 MB）
  macOS 用户   →「4-精简版-macOS-v0.8.zip」（不到 1 MB）

  ⚠️ 为什么要分开：以前一个包里塞了三套启动器（.bat / .sh / .command），
     长得几乎一样，谁都不知道该点哪个 —— 点在 Windows 专用的那个上
     没反应，点在 Linux 那个上弹一屏代码，还以为工具坏了。
     现在一个包只管一个系统，摊开来一眼就能看出该点哪个。

【三个包都自带「自检」和「先读这个」】
  · 包顶上有张「0-先读这个（第一次用）.txt」，只讲你这个系统的事，
    打开先看它，三句话就完事。
  · 里面有个「自检」文件夹：双击「一键自检」（Linux 上是开终端跑
    bash 自检/一键自检.sh），它会拿自带的测试素材真跑一遍，
    生成一份「自检报告.txt」。缺什么、错在哪一眼就看得出来 ——
    不用等插帧跑到一半才发现 rife 没配好。

  ★ Linux 用户特别注意一条：
    Linux 的文件管理器默认把 .sh 当**文本文件**打开 ——
    你双击「启动界面.sh」，多半只弹出一屏代码，程序一点动静都没有。
    这不是工具坏了。正确姿势是在文件夹里右键 →「在这里打开终端」，
    然后跑   bash 启动界面.sh
    想以后能双击的话，先跑一次   bash 装个桌面图标.sh
    它会在桌面放一个图标，以后双击那个就行。

  双击没反应 / 报错看不懂 → 包里附了一份「打不开看这里.txt」，
  按 Windows / Linux / macOS 分节写的，对号入座就行。

【三个包里都带了这些文档】
  · 说明书-保姆级教程.txt —— 纯文本，拿记事本打开就整齐，
    从装 Python 到排错一条龙，照着做就行
    （最新版加了「支持哪些格式」和「跑得有多快、占多少硬件」两节）
  · 打不开看这里.txt —— 双击没反应 / 黑框一闪 / 窗口不出来 / 权限不够 /
    缺 tkinter / 行尾是 CRLF，按系统分三节对号入座；末页有命令行兜底方案。
  · 自检/说明.txt —— 一键自检怎么用、会吐出一份什么样的报告。
  · 版本更新记录.txt —— v0.1 到 v0.8 每版改了啥，
    外加一份「实际踩过的坑」清单
  · README.md —— 带完整实测数据的参考手册

【新加的一个小东西：显卡自动绑独显】
每次运行开头，它会真跑一次最小任务，让 rife 自己把机器上
能用的显示设备报出来，长这样：

  [0] NVIDIA GeForce RTX 2060 〔独显〕 ← 用这块
  [1] Intel HD Graphics 530 〔核显〕
  [2] llvmpipe 〔软件渲染·极慢〕

然后脚本自己挑一块独显绑上。

为什么要自动挑：笔记本上核显常常排在 0、独显排在 1。
默认值要是写死成 0，那大部分笔记本用户会一直在跑核显，
还以为是这工具就这速度。

顺便说下软件渲染到底有多慢 —— 拿同一段 12 帧小素材试的：
绑独显 5 秒，强行指定 llvmpipe 软件渲染 29 秒，差 5.8 倍。
而且那还是个小片段（大头是模型加载这种固定开销），真素材差距更大。
真掉到软件渲染，脚本会明确警告你别硬跑。

懂行的想手动指定，config 里填 0 / 1 / 2 就行，默认 auto。

【顺便答一个肯定有人问的：目标帧率不是整数倍行不行】

行，一点问题没有。

  24fps → 72fps = 3.00 倍  （桌宠的主场景，正好整数）
  20fps → 48fps = 2.40 倍  （表情包这种不规矩的帧率）

非整数倍不会出错 —— RIFE 是在整条序列上均匀分布输出帧的，
出来永远是标准的固定帧率、时间轴均匀。唯一的代价是内容时间轴相对
播放时间被拉伸不到 1%（实测 0.78%），肉眼看不出来。

想最干净就挑整数倍：源素材 20fps 的话，40fps 或 60fps 最齐。

另外注意：如果某个片段的源帧率本来就不低于目标帧率，脚本会直接
跳过它 —— 插了反而是降帧。


【一个安全阈值，说一下】
默认只放开到 3 倍（24fps → 72fps），超过会拦下来，要强行跑得自己改配置。
但拦下来的理由是「功耗」，不是「画质」。
画质上连 120fps 都没看出毛病；真正的问题是 CPU 代价随帧率线性涨，
实测时 90fps 那批把 CPU 顶到了 75°C 触发了保护。
所以工具里加了「编码线程数」，填 2~3 能明显降温，代价是慢一点。

【最后】
· 这不是官方工具，也不是要改主仓库，就是个可选的生产线，
  不需要的完全不用理。
· 用之前自己备份原素材（脚本不碰原文件，但备份总是对的）。
· macOS 一行都没跑过 —— 有 Mac 的兄弟愿意帮忙试一下的话，
  感激不尽。
· 大佬们看出哪里写得蠢，愿意指点两句就太好了。

Q：为什么不做超分？
A：一是超分 106 个片段要跑几个小时；二是原素材本来就是 640×360 的，
   想要高清直接用原素材就行，不需要"造"一个高清出来。

Q：为什么不用 rife-anime？听说对二次元线条更友好？
A：实测比过 —— 同为 48fps、同帧号、同一片段，两个模型的逐像素
   RMSE 只有 0.61%，肉眼分不出差别。而 rife-anime 只能固定 2 倍、
   不支持自定义帧数，这个工具的核心就是任意目标帧率，所以默认 v4.6。
   （你如果正好好只想要 2 倍，可以在 config 里改成 rife-anime 自己试。）

Q：支持 mp4 吗？
A：目前只出 webm，是刻意的 —— mp4 的 H.264 装不下透明通道，
   一旦改成出 mp4，"带透明的素材不会丢"这个最大优点就没了。
   而且市面上能插帧、能出 mp4 的工具已经很多了，不差这一个。
   （普通不透明视频想转 mp4，插完帧再拿 ffmpeg 转一道就行。）

Q：怎么不并进主仓库？
A：本来就不是所有人都需要插帧，这是可选的生产线。
   硬塞主仓库反而是给别人添麻烦。

Q：会不会把素材搞坏？
A：只读你给的源目录、只写自己的输出目录，绝对不碰原文件。
   但还是建议自己备份一份。

Q：会不会很吃 CPU？
A：插帧那会儿会，平时不占。而且插完帧帧率上去了、分辨率可以降下来，
   长期看反而省电。实测同屏尺寸：原版 640×360 是 36.4%，
   换成 320×180 / 72fps 之后是 14.3%。

Q：为什么插帧还要保留 alpha 做两遍？
A：因为 VP9 的透明通道是单独一个平面存的。RIFE 只认图像，
   所以得把彩色和透明拆成两组各插一遍，最后再合起来。
   多花一倍时间，但这样透明边缘才不会糊掉。

Q：有没有鬼影？
A：在测过的 106 个片段和 48 / 72 / 90 / 120fps 四档、
   外加 8fps / 12fps 的极端低帧素材上，没看到明显的。
   但必须说清楚两件事：
   ① 素材只覆盖了 640×360 的 Q 版风格，细线条立绘、高速横向平移
      那类没有样本；
   ② 没有做任何"重影修复"后处理，RIFE 出什么就是什么，
      工具里没有那种自动去虚影的魔法。
   所以保守起见默认只放开到 3 倍，往上属于风险自负。
