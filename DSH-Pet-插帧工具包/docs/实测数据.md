DSH Pet 插帧工具 · 实测数据与方法
=====================================================
测试机：i7-6700（4核8线程）+ RTX 2060 6G + 16G 内存，Linux Mint 22.3 / X11
测试素材：桌宠内置角色，640×360 / 24fps / 241 帧 / 10.04 秒，VP9 + Alpha
工具版本：rife-ncnn-vulkan（rife-v4.6 模型）、ffmpeg、VP9 编码


一、插帧耗时与体积
----------------------------------------------------
目标帧率   倍数    输出帧数   单个片段耗时     输出体积
  48fps     2×       482      21 ~ 26 秒     0.4 ~ 1.2 MB
  72fps     3×       723      29 ~ 37 秒     0.5 ~ 1.5 MB
  90fps    3.75×     904      34 ~ 42 秒     0.6 ~ 1.7 MB
 120fps     5×      1205      43 ~ 56 秒     0.7 ~ 2.0 MB

（耗时含：拆帧 + 两次 RIFE 插帧（彩色/透明各一次）+ 合成编码。
  输出体积差异主要来自内容复杂度，同一档不同片段能差 3 倍。）


二、画质怎么测的（方法先讲清楚，免得被当成嘴炮）
----------------------------------------------------
1. 挑动作最猛的片段
   用 32×18 灰度缩略图逐帧算差分，找出帧间差最大的时刻。
   实测动作最猛的几个片段是：
        22.0  大口吃零食        t=8.46s
        18.8  吹气球            t=2.71s
        18.1  玩水枪            t=4.08s
        15.5  左转奔跑          t=4.58s
        12.3  原地跳跃抓碎头顶物品  t=7.08s

2. **按插帧相位对齐**（这一步很关键，不然后面对比全是错的）
   举例：源素材 24fps 的帧 110、111 之间是动作最快的区间。
   - 48fps：第 221 帧正好是半程 50%
   - 72fps：第 331 / 332 帧是 33% / 67%
   - 90fps：第 412 帧是 40%
   - 120fps：第 552 / 553 帧是 40% / 60%
   只有拿这些"插出来的帧"对比才有意义 ——
   如果按「同一时刻」取帧，取到的往往还是原始帧，那比的是取帧误差不是插帧质量。
   （第一版就踩过这个坑，差点得出错误结论。）

3. 量化指标：alpha 通道的「中间透明度占比」
   统计 alpha 值落在 25~230 之间的像素比例。边缘越糊、越容易藏鬼影，这个值越高。

        原始帧（参考）        0.66% / 0.70%
        48fps 插帧            0.76%
        72fps 插帧            0.75%
        90fps 插帧            0.80%
        120fps 插帧           0.76%

4. 肉眼复核
   把上述帧裁到边缘区域、放大 3 倍（点采样，看原始像素）并排比对。


三、画质结论
----------------------------------------------------

【3.1 最猛片段 · 峰值动作区间】大口吃零食，源帧 203↔204（t=8.46s）

    源 原始帧 203        12.10%
    源 原始帧 204        12.45%
    48fps 半程插帧       12.39%
    72fps 33% / 67%     12.31% / 12.40%
    90fps 40%           12.38%
    120fps 40% / 60%    12.34% / 12.40%

  → 所有插帧值都**落在两个源帧之间**，说明插帧没有带来额外边缘退化。
  → 放大 3 倍肉眼比对：线条、蕾丝、围裙图案都锐，
    **没有黑洞、融化或双层幻影 —— 120fps 也没有。**

【3.2 中等动作片段】左转奔跑（第一轮测试，按相位对齐）

    源 原始帧            0.66% / 0.70%
    48 / 72 / 90 / 120   0.75% ~ 0.80%
  → 同样的结论：只比原始帧「软」0.06~0.14 个百分点，量级很小。

【3.3 模型对比：rife-v4.6 vs rife-anime】
  同为 48fps（2 倍）、同帧号（第 340 帧，都是 50% 相位）、同一片段：

    rife-v4.6     中间 alpha 占比 2.42%
    rife-anime    中间 alpha 占比 2.42%
    逐像素 RMSE   0.61%

  → **两者肉眼分不出差别。** 所以没有理由为了 rife-anime 放弃"任意倍数"的能力，
    默认继续用 rife-v4.6（只有 rife-v4 系列支持自定义插帧倍数）。

⚠️ **必须说明的适用范围**
* 只测了 640×360 的 Q 版素材、2 个片段（其中一个是全库动作最猛的）；
* **细线条立绘、高速横向平移、强对比边缘的素材没有覆盖到** ——
  那类素材上 RIFE 更容易翻车；
* 所以工具默认把安全线设在 3 倍（72fps），属于**保守值**，
  而且**理由是功耗不是画质**（画质上没测出问题）。

📌 一句话：**画质上 90 / 120fps 也没看出毛病，但 CPU 会线性变贵；
   所以默认卡在 72fps，想往上得自己担风险。**


三·补、一个容易踩的坑（本工具踩过）
----------------------------------------------------
别按「同一时刻」取帧来比画质。

反面例子：源素材 24fps 时，t=4.583s 在 48 / 72 / 120fps 上分别是第
220 / 330 / 550 帧 —— 全是**整数倍**，也就全是**原始帧**，
根本没取到插出来的帧。这样比出来的差异是"取帧误差"，
第一版就因此差点得出「120fps 边缘发虚」的错误结论。

正确做法：**按帧号取**。例如 72fps 的第 331 / 332 帧 = 33% / 67% 相位，
那才是真正的插帧。

    # 按帧号抽帧（-vf select），别用 -ss 按时间抽
    ffmpeg -v error -c:v libvpx-vp9 -i 结果.webm -vf "select=eq(n\,331)" -frames:v 1 out.png


四、对桌宠运行的实际收益（这个才是大家真正关心的）
----------------------------------------------------
插帧本身**不省钱**（帧多了解码更费）。真正省电的做法是：
**用插帧把帧率提上去 → 换来可以把素材分辨率降下来 → 两笔账一起算才划算。**

同屏显示尺寸完全一样（窗口都是 640×390）时的四组实测：

配置 \ 素材                   原版 640×360 @24fps      本工具的 320×180 @72fps
---------------------------------------------------------------------------
上游官方默认配置               python  27.4%             python  58.3%
（prewarm=balanced             ffmpeg   9.0%             ffmpeg   7.0%
  idle_low_fps=false           ────────────              ────────────
  cache=8MB）                  合计    36.4%             合计    65.3%

本工具的调优配置                 python  15.3%             python  10.9%
（prewarm=minimal              ffmpeg   7.5%             ffmpeg   3.5%
  idle_low_fps=true            ────────────              ────────────
  cache=4MB）                  合计    22.8%             合计    14.3%
---------------------------------------------------------------------------
测量方法：启动后静置 115 秒 → top 每 10 秒采样 6 次 → 取平均。

【读出来的三件事】

1. **光提帧率、配置不动，反而更贵**（65.3% vs 36.4%）。
   拆开看：ffmpeg 那栏几乎没变（9.0% → 7.0%），python 那栏翻倍（27.4% → 58.3%）。
   → 解码成本 ≈ 跟「分辨率 × 帧率」走
   → 主进程每帧处理（镜像/预乘/缩放/掩码/重绘）≈ 主要跟「帧率」走，帧率×3 就×3

2. **配置调优的功劳很大**：同样素材从 36.4% → 22.8%（省 13.6 个百分点）。
   核心是 `idle_low_fps_enabled=true` —— 闲置 30 秒自动降帧，
   把"帧率"这个大杠杆直接掐掉。

3. **所以 72fps 素材必须配 `idle_low_fps_enabled=true`**，这是必要条件不是可选项。
   官方默认是 false，桌宠会一直全速跑，这时候 72fps 反而更吃亏。


五、硬件与安全
----------------------------------------------------
测试过程全程记录 CPU 温度与显存：

* 显存峰值 **480 MiB / 6144 MiB** —— 完全没有压力
* CPU 温度峰值 **75°C**（在 90fps 那批触发过一次保护）
* 平时（只跑桌宠）CPU 31 ~ 48°C，风扇约 1050 RPM

【降温手段：限制编码线程数】
加上 `编码线程数 = 3`（传给 ffmpeg 的 `-threads 3`）之后重测：

* 未经限制：90fps 那批 **触发保护（75°C）**
* 限制为 3 线程：48 / 72fps 那批 CPU 峰值 **70°C，0 次触发**
* 代价：单个片段从 29 秒变成 32~44 秒，慢大约 15%~30%

所以工具里加了这个配置项，**笔记本 / 小机箱 / 嫌风扇吵的建议填 2~3**。

另外脚本层还有两层保护：
1. `安全倍数上限`（默认 3.0），超过就拦下来；
2. 测试时额外挂了个看门狗：CPU ≥75°C 或显存 ≥5500MiB 就杀任务（这个没打进工具包）。


六、复现方法
----------------------------------------------------
# 插帧
python 插帧.py --试跑 1          # 先跑一个看看
python 插帧.py                    # 跑光 input/ 里的全部

# 校验输出（注意 -c:v libvpx-vp9，不加看不见 alpha）
ffprobe -v error -c:v libvpx-vp9 -select_streams v:0 \
        -show_entries stream=width,height,pix_fmt,r_frame_rate \
        -of default=nw=1 output/xxx.webm

# 找动作最猛的时刻（32×18 灰度逐帧差分）
ffmpeg -v error -c:v libvpx-vp9 -i 片段.webm -vf scale=32:18,format=gray -f rawvideo -

# 按帧号抽取插帧（而不是按时间），才能对齐相位
ffmpeg -v error -c:v libvpx-vp9 -i 插帧结果.webm -vf "select=eq(n\,331)" -frames:v 1 out.png


七、Windows 实测对照（同一台机器双系统）
----------------------------------------------------
测试机：和上面那台**是同一台机箱**，Windows 10 专业版 22H2 / 19045.6466，
Python 3.10.11。硬件完全一致：i7-6700 + RTX 2060 6G + 16G，
ST500DM002 机械盘 + Acer SA100 480GB SSD。

也就是说：不是"别人的机器也能跑"，是同一套硬件、同一套素材，两个系统各跑一遍。

素材：640×360 / 24fps / 4.917 秒 / 118 帧 / VP9 + Alpha
目标：48fps（2 倍） → 输出 236 帧

  步骤                耗时      占比
  拆彩色帧            0.3 秒      2%
  拆透明通道          0.3 秒      2%
  RIFE 彩色插帧       6.1 秒     40%
  RIFE 透明插帧       2.8 秒     18%
  合成编码            5.8 秒     38%
  ─────────────────────────────────
  合计               15.3 秒

输出规格校验通过：640×360 / 48fps / yuva420p / 时长一致。

与 Linux 对照（按素材时长折算）：
  Linux    2.35 秒耗时 / 秒素材
  Windows  3.11 秒耗时 / 秒素材   → 慢约 32%

Windows 慢的原因大概率是 NTFS 小文件 IO（拆帧阶段好几千个 png）
加上两边的 ffmpeg 构建不同。两周都在"十几秒出一段"的量级。

★ 这张表顺便证伪了一个常见误判：「插帧是不是纯 CPU 跑的？」
  RIFE 两步占总耗时 58%，拆帧+编码（磁盘 IO）占 42%。
  真是 CPU 软件渲染的话，这段素材要按分钟算，不是 15 秒。

Windows 上顺手验掉的「只在 Windows 才炸」的坑：

  解压后中文文件名（无 #U4e00 乱码）        ✔
  日志框中文（系统首选编码 cp936）           ✔ 不乱码
  双击 启动界面.bat（不弹黑框）              ✔
  运行中拖动/最小化（不假死）                ✔
  目标帧率填 abc → 弹「输入不合法」          ✔
  目标帧率填 120 → 安全线拦截 + 询问         ✔

cp936 那条最刁：它是简体中文 Windows 的默认编码，子进程往管道写中文时会用它，
而 GUI 按 UTF-8 读，不处理就是满屏乱码。这个 bug 在 Linux 上永远复现不出来。


八、显卡：自动挑独显 & 软件渲染有多慢
----------------------------------------------------
rife-ncnn-vulkan 启动时会把枚举到的显示设备打成 [序号 名字] 的行，
这是唯一能拿到"到底跑在哪块卡上"的办法 —— 命令行上 -g 只是个序号，
序号背后是哪块卡只有它自己知道。

本机实测报出来三块：
  [0] NVIDIA GeForce RTX 2060          〔独显〕
  [1] Intel(R) HD Graphics 530 (SKL GT2) 〔核显〕
  [2] llvmpipe (LLVM 20.1.2, 256 bits)   〔软件渲染·极慢〕

脚本按 独显 → 核显 → 软件渲染 的顺序自动挑。

为什么必须自动挑：笔记本上核显常排在 [0]、独显排在 [1]。
默认值写死成 0 的话，大部分笔记本用户会一直在跑核显，还以为是工具就这速度。

模拟 10 种真机组合验过挑选逻辑（因为本机独显正好在 0，测不出关键场景）：

  笔记本 · 核显在 0 / 独显在 1   → 挑中 [1] GTX 1650      ✔
  笔记本 · 独显在前              → 挑中 [0] RTX 4060      ✔
  台式 · 双独显                  → 挑中 [0] RTX 3080      ✔
  A 卡台式无核显                 → 挑中 [0] RX 6600       ✔
  只有核显（Intel）              → 退用 [0] HD 530       ✔
  只有核显（AMD APU）            → 退用 [0] Radeon      ✔
  只剩软件渲染                   → [0] llvmpipe + 警告   ✔
  Mac M 系列                     → 挑中 [0] Apple M2 Pro ✔
  Mac · Intel + AMD Pro          → 挑中 [1] Radeon Pro 555 ✔
  Microsoft Basic Render Driver  → 退用 + 当核显处理     ✔

★ 软件渲染到底有多慢（同一段 12 帧小素材）：
    自动绑独显 [0] RTX 2060     5 秒
    强行指定 [2] llvmpipe      29 秒      → 5.8 倍

  而且这还是个小片段（大头是模型加载这种固定开销），真素材差距会更大。
  所以真掉到软件渲染，脚本会明确警告别硬跑。


九、低帧素材能不能插（8fps / 12fps）
----------------------------------------------------
桌宠素材一般是 24fps，但有人可能拿更低的素材来插。这块单独测，
因为帧间隔越大、位移越大，RIFE 越容易算不准。

量化方法：alpha 平面缩到 160×90，算相邻帧平均绝对差。
  「跨源帧处」   = 源素材两个原帧之间的那一步
  「纯补帧处」   = 纯粹由 AI 补出来的那几步
  两者比值越接近 1，说明运动分布越均匀、越不抖。

  场景                        帧数   帧间差均值   最大跳变   跨源÷纯补
  源 8fps（原始）               80     4.063      33.78        —
  8fps → 48fps（6 倍）         480     0.831       8.47      0.79×
  源 12fps（原始）             120     2.924      30.02        —
  12fps → 48fps（4 倍）        480     0.840      10.07      0.83×
  对照：ffmpeg 帧复制升帧       480     0.670      33.78      0.00×

  最后一行是「不做插帧、只把帧复制 6 份」的对照组：比值 0.00
  （复制出来的帧和上一帧完全一样），然后突然跳 33.78 —— 这就是肉眼可见的抖。
  插帧把最大跳变从 33.8 压到 8.5。

透明通道也查了，没丢（alpha 通道三档占比）：

                  全透明    全不透明   半透明
  源 8fps          0.4%     15.6%     83.9%
  产物 48fps(6倍)   0.4%     15.6%     84.0%


十、本方法覆盖不到的地方（自己交代清楚）
----------------------------------------------------
1. 素材只覆盖 640×360 的 Q 版风格。细线条立绘、高速横向平移、
   强对比边缘那类没有样本 —— 而 RIFE 恰恰最容易在那类素材上翻车。
2. 90 / 120fps 样本偏少。
3. 8fps / 12fps 只测了一个片段（左转奔跑）。
4. ★ 工具里**没有任何"重影修复"后处理**。RIFE 出什么就是什么，
   脚本只是 拆帧 → 插帧 → 合帧 → 编码。
   上面所有数据只说明"在这批素材上没看出问题"，
   不代表它在任何素材上都不会出鬼影。
5. macOS 完全没实机跑过；AMD / Intel 显卡插帧也没在真机上验过
   （自动挑卡的逻辑覆盖了它们的名字特征，但没验过）。
