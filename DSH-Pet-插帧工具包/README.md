# DSH Pet 素材定制插帧工具

给 **webm 视频补帧**用的小工具：把 24fps 插成 48 / 72 / 90 / 120fps，
**保留透明通道**，输出还是 webm。

> **名字里虽然有「DSH Pet」，但它对任何 webm 都通用 —— 不是只给桌宠素材用的。**
>
> 实测跑通过的素材类型：
>
> | 素材 | 结果 |
> |---|---|
> | VP9 + 透明通道（桌宠素材、动态壁纸这类） | ✅ 透明通道原样保留 |
> | 不透明 VP9（普通视频、录屏） | ✅ 输出也不带多余的 alpha |
> | VP8（老编码的 webm） | ✅ 自动识别，输出转成 VP9 |
> | 任意分辨率（试过 320×240 / 360×200 / 640×360 / 1280×720） | ✅ 尺寸不用凑整 |
> | 带音轨的 webm | ✅ 音轨原样搬过去（不重编码） |
>
> 说人话：**带透明的它不会给你弄丢，带声音的它不会给你弄没。**
> 市面上不少插帧工具在这两点上会翻车。

> **先说清楚：这是一个可选的周边生产线，不是要改主仓库、也不是官方补丁。**
> 觉得动作有点顿、想让它更丝滑的可以试试；不需要的话完全不用理它。

## 一、先选一种用法

### 方式 A：图形界面（推荐小白用，鼠标点两下）

**双击「启动界面」**（Windows 是 `启动界面.bat` / Linux 是 `启动界面.sh` / macOS 是 `启动界面.command`），
然后：

```
① 点「选择…」挑源素材文件夹（默认就是本目录下的 input/）
② 点「选择…」挑输出文件夹（默认 output/）
③ 在「目标帧率」里填个数字（默认 72）
④ 点「▶ 开始插帧」，然后等进度跑完
```

界面长这样：三个输入项 + 一个大按钮 + 下面一个实时日志框。
跑的时候**界面不会卡死**（插帧逻辑跑在后台进程里），可以放着不管。

### 方式 B：命令行（极客用）

```
第 1 步  把要插帧的 webm 素材丢进 input/ 文件夹
第 2 步  双击「一键插帧」（Windows .bat / Linux .sh / macOS .command）
第 3 步  去 output/ 里拿结果，塞回桌宠的素材目录
```

命令行版支持更多参数，跑 `python 插帧.py --help` 看全部。

---

**但不管哪种方式，都得先准备两个外部程序**（下面第二节，一次性的事）。

> 💡 第一次跑建议先只放 **1 个文件** 进去试水，确认流程通了再整批丢。
> 图形界面里可以用文件夹选择器；命令行版可以把 `config.json` 里的
> 「只处理前N个文件」设成 1。

### 关于「素材放哪、结果去哪」（路径规则）

**放哪都行，不用非得用工具包里的 input/。** 规则是这样：

| 情况 | 输出会落在哪 |
|---|---|
| 图形界面：源选在 `D:\素材`，输出框别动 | 自动跟着变成 `D:\素材_插帧输出` |
| 图形界面：你自己改了输出框 | 尊重你选的，不再自动跟随 |
| 命令行：`python 插帧.py D:\素材` | `D:\素材_插帧输出` |
| 命令行：`python 插帧.py D:\素材 --输出 E:\结果` | `E:\结果` |
| 什么都不给（默认） | 工具包自带的 `output/` |

两个细节值得知道：

* 输出目录**刻意不放进源目录里面** —— 因为输出也是 `.webm`，
  放进源目录的话，下次再跑会把上一轮的产物当素材**又插一遍**，越滚越大。
* 输出目录带**源目录的名字**（`素材_插帧输出`），
  这样处理好几套素材时不会互相覆盖同名文件。

## 二、准备两个外部程序

工具本身**不需要 pip install 任何 Python 包**（故意的，这样最不容易装不上）。
它只调用两个现成的可执行文件：

### 1) ffmpeg（拆帧、合成、编码）

| 系统 | 怎么装 |
|---|---|
| **Windows** | 去 <https://www.gyan.dev/ffmpeg/builds/> 下 `ffmpeg-release-essentials.zip`，解压后把 `bin` 里的 `ffmpeg.exe` 和 `ffprobe.exe` 放到本工具包目录下 |
| **macOS** | `brew install ffmpeg` |
| **Linux** | `sudo apt install ffmpeg`（Debian/Ubuntu）／`sudo dnf install ffmpeg`（Fedora） |

### 2) rife-ncnn-vulkan（插帧本体）

到这里下预编译包，**选自己系统的那个**：
<https://github.com/nihui/rife-ncnn-vulkan/releases>

国内直连 GitHub 经常打不开，加个中转前缀就行：
`https://gh-proxy.com/https://github.com/nihui/rife-ncnn-vulkan/releases`

下完解压，把**整个文件夹**放到本工具包目录下（或者随便放哪，然后在
`config.json` 里把 `rife可执行文件路径` 填空成绝对路径）。

> 🍎 **macOS 用户注意**：macOS 的发布包是个 **`rife-ncnn-vulkan.app`** 包，
> **整个 `.app` 丢进本工具包目录就行**，不用进去翻可执行文件 ——
> 脚本会自己穿进 `.app` 里找到可执行文件，也会自动到
> `Contents/Resources/` 下找模型。
> 另外 macOS 会给下载来的程序打「隔离标记」，脚本已经自动帮你放行了
> （`xattr -dr com.apple.quarantine`）；万一还是被系统拦下，
> 手动在终端里对 `.app` 跑一次这个命令即可。

> 放好之后跑一次 `python 插帧.py --检查`，它会告诉你找没找到，找不到会给出提示。

## 三、配置说明（`config.json`）

改这个文件就行，改完保存再运行。**所有路径留空 = 自动在系统里找。**

| 字段 | 默认 | 说明 |
|---|---|---|
| `目标帧率` | `72` | 想要多少帧就填多少。脚本会自己读原素材帧率、算出插几倍 |
| `插帧模型` | `rife-v4.6` | **别改**。只有 `rife-v4` 系列能自定义倍数；`rife-anime` 只能固定 2 倍，填了别的帧率脚本会拦下来 |
| `性能模式` | `auto` | 探核 → 自动决定线程预算 + 压低优先级。`全速` / `省电` / `手动` 可选，见 4.6 节 |
| `临时帧目录` | 空 | 留空 = 自动挑（优先内存盘）。见 4.7 节 |
| `使用第几块显卡` | `auto` | **默认自动挑独显**，一般不用动。想手动指定就填 `0` / `1` / `2`。详见 4.4 节 |
| `视频质量CRF` | `32` | 越小画质越好体积越大，VP9 用 28~34 比较均衡 |
| `视频码率kbps` | `0` | 填 0 = 按 CRF 走（推荐）。想锁死码率就填比如 `800` |
| `编码速度cpu-used` | `4` | VP9 速度旋钮，0=最慢最好。**别填 5/6，那反而比 4 慢**。见 4.6 节 |
| `编码实时模式` | `true` | 再快一档（关掉前瞻）。想极限画质改 `false` |
| `编码线程数` | `0` | 0 = 让「性能模式」自动决定 |
| `rife读写线程` | `"1:2:2"` | rife 的 读:算:写 线程数。填 `1:1:1` 能少抢 CPU，代价是慢 30% |
| `保留音频` | `true` | opus / vorbis 原样复制；别的（aac 等）自动转 opus —— webm 装不下它们 |
| `安全倍数上限` | `3.0` | 实测出来的安全线，见第五节 |
| `允许超过安全倍数` | `false` | 想插更高帧率就改成 `true`（画质风险自负） |
| `只处理前N个文件` | `0` | 0 = 全部处理。想先试一两个就填 1 |
| `处理完删除临时帧` | `true` | 关掉的话拆出来的 png 会留着（很占地方，调试用） |

### 输入格式：全自动，不用挑

认得这些后缀，编码也是自动识别的（VP9 / VP8 / AV1 / H.264 / MPEG-4 …）：

```
.webm  .mkv  .mp4  .mov  .m4v  .avi  .wmv  .flv  .ts  .m2ts
.mpg   .mpeg .ogv  .3gp  .webp .gif  .apng
```

**输出永远是 `.webm`** —— 带透明的视频实际能用的容器只有它，而且 ffmpeg
是按后缀选封装格式的，不写死的话 mp4 会原样吐一个 mp4 出来（透明还丢了）。

音轨也会自动处理：opus / vorbis 原样复制，aac / mp3 之类自动转 opus。

> 💡 **透明度是按"实际内容"判断的，不是按像素格式。** 有些格式（最典型是 GIF）
> 会声明一个透明索引却从不使用，解出来像素格式带 alpha、实际上全是不透明的。
> 脚本会扫一遍 alpha 帧再决定要不要跑那轮插帧 —— 实测能省 26% 时间，
> 输出也不会莫名其妙带个空通道。判不准时一律当"有 alpha"，绝不会把真的透明丢掉。

> 🧱 **一堵修不动的墙**：`mp4` / `mov` 容器**装不下透明通道**。
> 带 alpha 的素材一 remux 进 mp4，透明当场就没了（`yuva420p` → `yuv420p`）。
> 这是格式限制，不是工具的问题 —— 工具最多能做到"把 mp4 里的画面读出来、
> 插完帧再装回 webm"，但素材在 mp4 里的时候就已经没有透明了。

## 四、实测数据

测试环境：i7-6700 + RTX 2060 6G，Linux，素材 640×360 / 24fps / 241 帧 / 10 秒。

### 4.1 插帧耗时与体积

| 目标帧率 | 倍数 | 输出帧数 | 单个片段耗时 | 输出体积 |
|---|---|---|---|---|
| 48fps | 2× | 482 | 21 ~ 26 秒 | 0.4 ~ 1.2 MB |
| 72fps | 3× | 723 | 29 ~ 37 秒 | 0.5 ~ 1.5 MB |
| 90fps | 3.75× | 904 | 34 ~ 42 秒 | 0.6 ~ 1.7 MB |
| 120fps | 5× | 1205 | 43 ~ 56 秒 | 0.7 ~ 2.0 MB |

### 4.2 画质（这个才是重点）

**测法**：先扫一遍全部 106 个片段，按 32×18 灰度逐帧差分找出**动作最猛的那个**
（结果是「大口吃零食」，峰值帧间差 22.0，比一般片段高 1.4 倍）。
然后在峰值动作区间上，**按插帧相位对齐**取帧（这一步很关键，见下），
放大 3 倍逐像素比对，并用 alpha 的「中间透明度占比」量化边缘发虚程度（越低越干净）。

**结果 1：最猛片段 · 峰值动作区间**

| 帧 | 中间 alpha 占比 |
|---|---|
| 源 原始帧 203 | 12.10% |
| 源 原始帧 204 | 12.45% |
| 48fps 半程插帧 | 12.39% |
| 72fps 33% / 67% | 12.31% / 12.40% |
| 90fps 40% | 12.38% |
| 120fps 40% / 60% | 12.34% / 12.40% |

**插帧值全部落在两个源帧之间** —— 也就是说插帧没有带来额外的边缘退化。
肉眼放大看，48 / 72 / 90 / 120 的线条、蕾丝、围裙图案都锐，
**没有黑洞、融化或双层幻影，120fps 也没有。**

**结果 2：rife-v4.6 vs rife-anime（同为 48fps、同帧号、都是 50% 相位）**

| | 中间 alpha 占比 |
|---|---|
| rife-v4.6 | 2.42% |
| rife-anime | 2.42% |

逐像素比对 **RMSE = 0.61%**，肉眼分不出差别。
**结论：在这个素材上没有理由为 rife-anime 放弃"任意倍数"的能力**，
所以默认仍然用 `rife-v4.6`（只有它支持自定义插帧倍数）。

> ⚠️ **范围说明**：以上是 640×360 的 Q 版素材、两个片段（含最猛的那个）。
> **细线条立绘、高速横向平移、强对比边缘的素材没有覆盖到** ——
> 那类素材上 RIFE 更容易翻车。所以下面的安全建议是**保守值**。

> 🕳️ **一个容易踩的坑（本工具踩过）**：别按「同一时刻」去取帧比画质。
> 比如源素材 24fps 时，`4.583 × 48 / 72 / 120` 全是整数 ——
> 取到的**其实都是原始帧，不是插出来的帧**，那比的是取帧误差不是插帧质量。
> 必须按**帧号**取（比如 72fps 的第 331 帧 = 33% 相位），才有意义。

### 4.3 对桌宠的实际收益

插帧本身不省钱（帧多了解码更费），但**帧率提上去之后可以把素材尺寸降下来**，
两笔账一起算才划算。同屏显示尺寸一样（窗口都是 640×390）时实测：

| 素材 | python 端 | ffmpeg 端 | 合计 CPU |
|---|---|---|---|
| 原版 640×360 @24fps | 27.4% | 9.0% | **36.4%** |
| 本工具的 320×180 @72fps | 58.3% | 7.0% | **65.3%** |
| 原版 640×360 @24fps + 调优配置 | 15.3% | 7.5% | **22.8%** |
| 本工具的 320×180 @72fps + 调优配置 | 10.9% | 3.5% | **14.3%** |

**看出来了吗**：光把帧率提上去、配置不动，反而更贵（65.3%）。
真正省电的是配套的三条配置：

- `media_prewarm` 改成 `minimal`（别在启动时把所有动画都预热一遍）
- `idle_low_fps_enabled` 改成 `true`（闲置 30 秒自动降帧 —— **这条是 72fps 的必要条件**）
- `first_frame_cache_max_mb` 调小一点

完整报告见 `docs/实测数据.md`。

### 4.4 显卡：脚本会自己挑一块独显绑上

插帧本体是 `rife-ncnn-vulkan` —— **走 Vulkan 跑显卡的，不是 CPU。**
但「跑在哪块卡上」这件事很坑，所以脚本每次运行开头都会**真跑一次最小任务**，
让 rife 自己把机器上的显示设备报出来（多花 1~2 秒）：

```
可用显示设备（rife 自己报的，不是你猜的）：
   [0] NVIDIA GeForce RTX 2060  〔独显〕  ← 用这块
   [1] Intel(R) HD Graphics 530 (SKL GT2)  〔核显〕
   [2] llvmpipe (LLVM 20.1.2, 256 bits)  〔软件渲染·极慢〕
✅ 自动绑到 [0] NVIDIA GeForce RTX 2060 上（独显）。
```

**为什么要自动挑**：笔记本上核显经常排在 `[0]`、独显排在 `[1]`。
如果默认值写死成 `0`，那大部分笔记本用户会**一直在跑核显**，
还以为是这工具就这速度。

**自动挑选的优先级**：独显 → 核显 → 软件渲染。
`使用第几块显卡` 填 `auto`（默认）走自动；懂行的填 `0` / `1` / `2` 手动指定，
填错了会直接提示你改成哪一块。

**软件渲染到底有多慢**（同一段 12 帧小素材实测）：

| 跑在哪 | 耗时 |
|---|---|
| 自动绑独显 `[0] RTX 2060` | **5 秒** |
| 强行指定 `[2] llvmpipe` 软件渲染 | **29 秒** |

**5.8 倍** —— 而这还是个小片段（大头是模型加载这种固定开销）。
真素材差距会更大。所以真掉到软件渲染了，脚本会明确警告你别硬跑。

### 4.5 低帧素材能不能插（8fps / 12fps）

桌宠素材一般是 24fps，但有人可能会拿更低的素材来插。
这块单独测过，因为**帧间隔越大，RIFE 越容易翻车**（位移太大它算不准）。

量化方法：把 alpha 平面缩到 160×90，算相邻帧的平均绝对差。
「跨源帧处」= 源素材原帧之间的那一步；「纯补帧处」= 纯粹由 AI 补出来的那几步。
**两者越接近 1，说明运动分布越均匀、越不抖。**

| 场景 | 帧数 | 帧间差均值 | 最大跳变 | 跨源帧 ÷ 纯补帧 |
|---|---|---|---|---|
| 源 8fps（原始） | 80 | 4.063 | **33.78** | — |
| **8fps → 48fps（6 倍）** | 480 | 0.831 | **8.47** | **0.79×** |
| 源 12fps（原始） | 120 | 2.924 | **30.02** | — |
| **12fps → 48fps（4 倍）** | 480 | 0.840 | **10.07** | **0.83×** |
| 对照：ffmpeg 帧复制升帧 | 480 | 0.670 | 33.78 | **0.00×** |

最后一行是**「不做插帧、只把帧复制 6 份」的对照组** —— 它的比值是 `0.00`
（复制出来的帧和上一帧完全一样），然后突然跳 33.78。
这就是肉眼能看见的抖。本工具的插帧把最大跳变从 **33.8 压到 8.5**。

透明通道也检查了，**没丢**：

| | 全透明 | 全不透明 | 半透明 |
|---|---|---|---|
| 源 8fps | 0.4% | 15.6% | 83.9% |
| 产物 48fps（6 倍） | 0.4% | 15.6% | 84.0% |

> 🚫 **必须说清楚的一件事：工具里没有任何"重影修复"后处理。**
> RIFE 出什么就是什么，脚本只是拆帧 → 插帧 → 合帧 → 编码。
> 上面那些数据说明的只是「在这批素材上没看出问题」，
> 不代表它在任何素材上都不会出鬼影。

### 4.6 性能：编码参数 + 自动调度

**先说一个反直觉的发现**：把整条流水线逐段计时之后，最贵的**不是插帧，是编码**。

| 阶段 | 耗时 | 峰值 CPU |
|---|---|---|
| 拆帧（一次解码出两组） | 0.9 秒 | ~785%（只有 1 秒的尖峰） |
| RIFE 插帧（彩色 + 透明） | 10.8 秒 | ~336% |
| **编码（VP9）** | **5.4 秒** | ~264% |
| **合计** | **18.8 秒** | |

而 ffmpeg 里 VP9 的默认值是 `cpu-used=0`（最慢最好）——原来一个旋钮都没设。

| 编码设置 | 耗时 | 峰值 CPU | 体积 | SSIM |
|---|---|---|---|---|
| `cpu-used=0`（原来的默认） | 13.09 秒 | 364% | 1257 KB | 基准 |
| `cpu-used=4` | 7.40 秒 | | 1446 KB | 0.9966 |
| **`cpu-used=4` + `deadline realtime`** | **5.35 秒** | **264%** | 1435 KB | 0.9964 |

**时间 -59%、峰值 CPU -28%、画质肉眼无差别**（体积 +14%）。

> ⚠️ 顺便挖出一个坑：`cpu-used=5` / `6` **反而比 4 慢**（9.5 / 9.2 秒）。
> libvpx 这个参数配合 `-row-mt` 时不是单调的，**4 才是拐点**。

**性能模式（默认 `auto`）** 会自动做四件事：

```
① 探核      用 sched_getaffinity 而不是 os.cpu_count()，
            被 taskset / cgroup 限制过也算得对
② 算预算    编码实测只吃约 2.2 个核 → 核多的机器根本不限线程
            （限了只是白白变慢）；4 核及以下才限制，留核给用户
③ 压优先级  Linux/macOS：nice -n 10 + ionice -c 3（IO 降到空闲级）
            Windows：BELOW_NORMAL_PRIORITY_CLASS
④ 打日志    把决定过程写出来，不玩黑箱
```

**为什么用 nice 而不是"少开线程"**（实测）：

- 机器**闲着**时，`nice 0` 和 `nice 19` 是 5.9 / 6.2 秒 —— **零成本**
- 机器**被压满**时，`nice 19` 把对用户的干扰从 **+11.5% 降到 +5.2%**

也就是说：**闲时全速抢，一开别的程序它自动让路**，内核免费帮你仲裁。

四种模式的实测（640×360 / 241 帧 → 48fps）：

| 模式 | 墙钟 | **总 CPU 工作量** | 平均占用 | 说明 |
|---|---|---|---|---|
| 旧版 | 27.6 秒 | 68.3 CPU秒 | 247% | —— |
| **auto** | **19.5 秒** | **40.8 CPU秒** | 209% | 默认，推荐 |
| 省电 | 26.8 秒 | 40.8 CPU秒 | **152%** | 活儿一样多，但摊薄了 |
| 全速 | 19.9 秒 | 42.1 CPU秒 | 212% | 不管别人 |

> ★ **三个数字别混**：总 CPU 工作量 = 真·电费（auto 比旧版少 **40%**）；
> 平均占用 = 你感觉得到卡不卡；峰值 = 会不会突然卡一下。
> **「省电」模式其实不省电**（总工作量一模一样），它是让你感觉得到的那部分
> 变小 —— 同时只占 1.5 个核，而不是 2.1 个。

### 4.7 中间帧放哪（顺手解决的一个真问题）

一趟插帧要拆出几百上千张小 png（几百 MB）。这些文件落在**机械硬盘**上，
会把整台机器拖得一顿一顿的 —— 这比吃 CPU 更容易让人骂人。

```
Linux / macOS ：优先 /dev/shm 或 /tmp（先确认它真的是内存盘）
Windows       ：先找虚拟内存盘（GetDriveTypeW 能认出来），
                没有就用 %TEMP%，并在日志里提醒"如果是机械盘建议改到 SSD"
手动指定      ：config.json 的「临时帧目录」填路径，优先级最高
```

> 实测这台机器上自动选中了 `/dev/shm`（内存盘，7.8 GB），用完自动清干净。

## 五、⚠️ 安全帧率说明（重要）

**默认建议：24fps 原素材插到 72fps（3 倍）就够了。**

理由**不是画质**，而是**功耗和负载**：

1. **144Hz 显示器 ÷ 72 = 2**，整数倍不抖；
2. **CPU 代价随帧率线性涨** —— 主进程每一帧都要做镜像、预乘、缩放、掩码重建、重绘，
   实测 120fps 比 72fps 贵将近一倍。笔记本 / 小机箱容易吃不消；
3. 画质上本工具**没测出** 90 / 120fps 有可见的鬼影（连最猛的片段都干净），
   但样本只有两个 640×360 的 Q 版片段，**细线条立绘没覆盖**，所以不放开。

所以脚本默认设了 `安全倍数上限 = 3.0`：你填 120 而原素材是 24fps 时，
它会**直接拦下来**并告诉你为什么。确认要试，就把 `允许超过安全倍数` 改成 `true`。

### 关于「倍数是不是整数」

脚本会先读源帧率、再算出目标帧数（`源帧数 × 目标帧率 ÷ 源帧率`）。
**不是整数倍也能跑**，但值得知道其中差别：

| 源 → 目标 | 倍数 | 齐不齐 |
|---|---|---|
| 24fps → 72fps | 3.00× | **整数 ✔**（桌宠的主场景） |
| 24fps → 48fps | 2.00× | **整数 ✔** |
| 24fps → 90fps | 3.75× | 非整数 |
| 20fps → 48fps | 2.40× | 非整数 |
| 20fps → 60fps | 3.00× | **整数 ✔** |

非整数倍**不会出错** —— RIFE 的 `-n` 是**在整条序列上均匀分布**输出帧的，
输出永远是标准 CFR，时间轴是均匀的。唯一的代价是内容时间轴相对播放时间轴
被拉伸不到 1%（实测 20→48fps 是 0.78%），肉眼看不出来。

**想最干净就选整数倍**：源 20fps 的话，40fps（2×）或 60fps（3×）最齐。

> 💡 顺带一个自适应：如果某个片段的源帧率**已经不低**于目标帧率
> （比如素材里混了一个 60fps 的片段，而你在插到 48fps），
> 脚本会**自动跳过它** —— 插了反而是降帧。

**如果你确实要跑 90 / 120fps，建议同时把 `编码线程数` 设成 2~3** ——
实测能把 CPU 峰值压下来一大截（实测时，90fps 那批把 CPU 顶到 75°C 触发了保护，
加上线程限制之后就没再触发过）。

## 六、常见问题

**Q：跑起来报 `$'\r': command not found` 或者一堆奇怪的 `^M`**
A：文件行尾被 Windows 编辑器改成 CRLF 了（bash 只认 LF，`.py` / `.json` / `.md` 不受影响）。
**修法：在终端里跑一次 `python 插帧.py`** —— 它启动时会自动把同目录下
`.sh` / `.command` / `.py` / `.json` / `.md` / `.txt` 的 CRLF 全部修回 LF，并告诉你改了哪些文件。
（`.bat` 是 Windows 原生格式，必须保留 CRLF，所以不在修复范围内。）

> 为什么自愈放在 Python 里而不是放在 bash 脚本里？因为倒霉的 bash **读到 CR 就已经崩了**，
> 它没机会自救 —— 这个坑本工具踩过，所以改成让 Python 来兜底。

**Q：提示找不到 ffmpeg / rife-ncnn-vulkan**
A：跑 `python 插帧.py --检查`，它会告诉你缺哪个、去哪下。
下完把文件夹放进工具包目录，或者在 `config.json` 里填绝对路径。

**Q：提示「模型 rife-anime 不支持自定义倍数」**
A：`rife-anime` 只能固定 2 倍。想用别的帧率就改回 `rife-v4.6`；
如果你正好只要 48fps（2 倍），可以试试 `rife-anime`，理论上对二次元线条更友好。

**Q：显卡显存不够 / 报 Vulkan 相关错误**
A：先看运行开头打印的「可用显示设备」——如果只有 `llvmpipe`，
说明你的显卡驱动没装好、现在跑的是软件渲染，那个会慢几十倍。
驱动正常的话，把 `使用第几块显卡` 改成 `auto` 或换另一块试试；
素材分辨率特别大的话先降分辨率再插帧。
（实测 640×360 时显存只用了 456MB，6G 卡完全够。）

**Q：太慢了**
A：插帧速度主要看显卡。可以按片段分批跑，脚本支持**续跑** ——
已经生成好的文件再次运行会自动跳过。

**Q：解压出来文件名变成 `#U4e00#U952e…` 这种乱码怎么办？**
A：这是**压缩包没带 UTF-8 文件名标志位**导致的，跟中文文件名先天不合。
- 本工具包是用带 UTF-8 标志位的方式打的（已在 Linux/Windows 常规解压工具上验证），正常不会出问题；
- 万一你还是遇到了，**换 7-Zip 或 WinRAR 解压**即可，别用老的命令行 `unzip`；
- 顺带一提：**桌宠发行版里那批 `#Uxxxx` 素材名，多半就是这个环节产生的** ——
  所以这不是作者故意加密，是打包/解压工具把非 ASCII 文件名转义了。

**Q：跑完发现某个片段坏了**
A：删掉 `output/` 里那一个，重新跑一次，其他的会自动跳过。

## 十、Windows 实测记录

**测试机型**：Windows 10 专业版 22H2（内部版本 19045.6466），Python 3.10.11

顺便说个可能有点意思的事 —— **测试用的 Windows 和开发用的 Linux
是同一台机器双系统**。也就是说：

```
i7-6700 / 16GB / RTX 2060 6GB
ST500DM002 机械盘 + Acer SA100 480GB SSD
```

同一套硬件、同一套素材，两个系统各跑一遍。所以下面的数据不是
「朋友说能跑」，是可比对照。

### 10.1 实机跑通的全流程

素材：`640×360 / 24fps / 4.917 秒 / 带透明通道 / 118 帧`
目标：`48fps`（2 倍），输出 `236 帧`

| 步骤 | 耗时 | 占比 |
|---|---|---|
| 拆彩色帧 | 0.3 秒 | 2% |
| 拆透明通道 | 0.3 秒 | 2% |
| **RIFE 彩色插帧** | **6.1 秒** | 40% |
| **RIFE 透明插帧** | **2.8 秒** | 18% |
| 合成编码 | 5.8 秒 | 38% |
| **合计** | **15.3 秒** | |

输出规格校验通过：`640×360 / 48fps / yuva420p / 时长一致`。

和 Linux 对比：Linux 同规格折算约 **2.35 秒耗时 / 秒素材**，
Windows 是 **3.11 秒 / 秒素材** —— Windows 慢约三成
（NTFS + 不同 ffmpeg 构建，正常范围），两边都是"十几秒出一段"的量级。

> 💡 这张表顺便回答了一个常见的误判：「插帧是不是纯 CPU 跑的？」
> 不是。RIFE 那两步占了 **58%** 的耗时，拆帧和编码（磁盘 IO）占 42%。
> 要是真掉到 CPU 软件渲染，一段素材是几十分钟起步，不是十几秒。

### 10.2 顺便验掉的几个「只在 Windows 才炸」的坑

| 项目 | 结果 |
|---|---|
| 解压后中文文件名 | ✅ 正常中文，没有变成 `#U4e00#U952e` |
| 日志框里的中文（**系统首选编码 `cp936`**） | ✅ 不乱码 |
| 双击 `启动界面.bat` | ✅ 不弹黑框、界面正常 |
